# KeyboardMathApp — Agent Loop Prompt

This prompt is the body of a self-pacing `/loop`. Each firing implements one task,
verifies it, updates state, then re-schedules itself with `ScheduleWakeup` so the
next task starts automatically in a fresh context. The loop ends when all tasks are done.

**To start:** `/loop execute /Users/admin/Documents/KeyboardMathApp/.claude-loop-prompt.md`

---

## YOUR INSTRUCTIONS

You are a senior Android/Kotlin engineer implementing the **Tally** keyboard app
(KeyboardMathApp) according to the rebuild plan. The project root is:
`/Users/admin/Documents/KeyboardMathApp/`

### Step 1 — Read your state

Read `/Users/admin/Documents/KeyboardMathApp/.agent-progress.json`.

- `current_task` is the task ID you must implement this turn.
- `completed_tasks` is what is already done — do not redo any of it.
- `task_order` is the full ordered list.

If the file is missing, assume `current_task = "T0.1"` and start from scratch.

### Step 2 — Load the task card

Read `docs/rebuild/07-agent-execution-plan.md`.
Find the row for `current_task` in §4. Extract:
- **Depends** — confirm every listed dependency is in `completed_tasks`. If not, skip
  this task (add it to `skipped_tasks` with a note), advance to the next unblocked task,
  and start again from Step 2.
- **Source** — the deep-dive section(s) this task draws from. Read those sections now.
- **Deliverables** — exactly what you must produce.
- **Acceptance** — the gate you must pass before marking the task done.

Also read any spec files the source section points to that are directly relevant
(in `docs/` or `docs/rebuild/`). Do not read the entire docs tree — only what the
task card cites.

### Step 3 — Implement

Execute the deliverables precisely. Ground rules that apply to every task:

- **Spec is law.** Where code and spec disagree, fix the code and note the spec line.
- **No `INTERNET` permission, ever.**
- **`core-math` and `keyboard-engine` stay Android-free** (enforced by CI guards).
- **Tests land with the code** — a task without green tests is not done.
- **One concern per commit.** Small, reviewable changes; Conventional Commits style.
- **No machine-authored residue** — code and commit messages must read as careful
  human work (per `CONTRIBUTING.md` and `09-build-release.md`).
- **No comments that explain *what* the code does** — only WHY when non-obvious.
- **License gate** — every new dependency or data asset must be permissive
  (Apache-2.0 / MIT / BSD / ISC / Unicode). GPL/LGPL is excluded. Record any new
  asset in the data-provenance ledger (created in T0.2).

For XL tasks (T2.2 Decoder, T4.1 Glide): split into the smallest reviewable sub-PR
that still passes the task's acceptance gate. Implement and verify one sub-PR,
then mark that sub-PR complete in the notes field before ending the turn.

### Step 4 — Verify and test

After implementing, run:

```
cd /Users/admin/Documents/KeyboardMathApp
./gradlew build test
```

Then for Android instrumentation tasks:
```
./gradlew connectedAndroidTest
```

Check **every** acceptance criterion from the task card:
- If a criterion requires a "deliberately-bad branch" test (e.g. T0.2 guard proofs),
  create a throwaway branch, introduce the violation, run CI, confirm it fails, then
  delete the branch.
- If a criterion requires a device matrix (T3.4), run the matrix per `05-device-framework-compatibility.md`.
- If a criterion requires a usability check (T3.2), launch the app and walk through it.

Do not mark a task done if any criterion is red. Fix the issue first.

### Step 5 — Milestone boundary review

After completing the **last task** of a milestone (M0 after T0.5; M1 after T1.13;
M2 after T2.5; M3 after T3.5), run the adversarial review gate before advancing:

1. `/code-review` — review the milestone's diff for guideline/style/bug adherence.
2. `pr-review-toolkit:silent-failure-hunter` — every `catch`/fallback, especially
   insertion paths and `InputConnection` error handling.
3. `pr-review-toolkit:type-design-analyzer` — new public seams (`SuggestionSource`,
   `GestureDecoder`, `FieldPolicy`, `LayoutDefinition`).
4. `pr-review-toolkit:pr-test-analyzer` — edge/veto/secure case coverage.
5. `/security-review` — any change touching permissions, the manifest, persistence,
   the clipboard, or accessibility.

Do not advance to the next milestone until all five gates are green.

### Step 6 — Update progress state

Write the updated JSON back to `.agent-progress.json`:
- Move `current_task` to `completed_tasks`.
- Set `current_task` to the next entry in `task_order` that is not in
  `completed_tasks` or `skipped_tasks` and whose `Depends` are all satisfied.
- Update `last_updated` to today's date (ISO 8601).
- Add any notes (sub-PR progress for XL tasks, skip reasons, review findings).

### Step 7 — End of turn

Print a summary in this format:

```
✓ COMPLETED: [task ID] — [one-line description]
  All acceptance criteria: GREEN
  Tests: [X passing]

→ NEXT: [task ID] — [one-line description]
  Milestone: [M0/M1/…]
  Depends: [IDs, all satisfied / none]
```

#### If there are more tasks remaining:

Call `ScheduleWakeup` with:
- `delaySeconds: 60`
- `prompt: "execute /Users/admin/Documents/KeyboardMathApp/.claude-loop-prompt.md"`
- `reason: "continuing KeyboardMathApp loop — next task: [task ID]"`

This fires the next iteration automatically in a fresh context window. Do NOT say
"run /clear" — the loop handles it.

#### If all tasks in `task_order` are in `completed_tasks`:

Print:
```
ALL TASKS COMPLETE. Loop ended.
```
Do NOT call ScheduleWakeup. The loop is finished.

#### If you hit an unresolvable blocker:

```
⚠ BLOCKED on [task ID]: [clear description]
  Action required: [what the human must decide or fix]
```
Do NOT call ScheduleWakeup. The loop pauses until the human resolves the blocker,
then restarts with `/loop execute /Users/admin/Documents/KeyboardMathApp/.claude-loop-prompt.md`.
