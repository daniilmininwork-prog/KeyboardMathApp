# Build, CI & release

How the project is built, verified, and shipped. The themes are: reproducible, verifiable, and
free of any "this was machine-generated" residue.

## Toolchain & project setup

- **Language:** Kotlin. **Build:** Gradle with the Kotlin DSL and a centralised version catalog
  (`libs.versions.toml`) so versions are pinned in one place.
- **Modules:** the multi-module layout from [system architecture](04-system-architecture.md)
  (`core-math`, `feature-glue`, `ime`, `overlay`, `app`, optional `design-system`).
- **`core-math` is a plain JVM/Kotlin library** (no Android plugin) so it tests fast and stays
  Android-free.
- **SDK targets:** min SDK **API 26 (Android 8.0)** as the baseline (broad coverage in 2026, no
  legacy IME quirks); compile/target the latest stable SDK. Any use of a newer API requires a
  guarded fallback to the baseline. (Confirm exact numbers at kickoff.)
- **Java/Kotlin/AGP versions** pinned in the version catalog and CI.

## Dependency policy

- **Minimal.** Each dependency on a keyboard is attack surface; justify every one in review.
- **Pinned + verified.** No dynamic version ranges; enable Gradle dependency verification
  (checksums/signatures) per [security](07-security-privacy.md).
- **No data-collecting SDKs.** No analytics/ads/crash-reporting that transmits off device.

## Continuous integration (GitHub Actions)

Pipelines, all required before merge to the default branch:

- **Verify:** ktlint + detekt + Android Lint; fail on issues.
- **Test:** `core-math` unit/property/golden/fuzz; `feature-glue` tests; instrumentation tests on
  an emulator profile; coverage threshold (high for `core-math`).
- **Security guards:** manifest permission allowlist (fails on `INTERNET`), `core-math`
  Android-free check, no-text-logging check; dependency vulnerability scan; SBOM artifact.
- **Build:** assemble debug; assemble release (unsigned) to catch R8 issues early.
- **Reproducibility (release branches):** build twice and compare outputs.

CI runs on pull requests and the default branch. Branch protection requires green CI and review.

## Release builds

- **R8/ProGuard:** enabled for release; strips debug logging, shrinks, obfuscates. Keep rules
  minimal and reviewed.
- **Signing:** release keystore lives outside the repo (CI secret / local secure store); never
  committed. Signing config reads from environment/secret, not source.
- **Outputs:** an AAB for Play (the IME), and — only if the overlay ships — a signed universal
  APK for off-Play direct download.
- **Versioning:** semantic version + monotonic version code; tags drive releases; a
  `CHANGELOG.md` in Keep a Changelog format is updated each release.

## Distribution

Per [platform strategy](03-platform-strategy.md), the product is **closed-source and ships
through Google Play**:

- **Google Play (primary, IME):** the keyboard product. Complete the **Data Safety** form as "no
  data collected / no data shared," backed by the absent `INTERNET` permission. The keyboard mode
  is Play-policy-clean.
- **Overlay mode (unresolved channel):** Google Play's Accessibility policy makes the overlay a
  likely-rejected fit, and there is no F-Droid option for a closed-source app — so the overlay
  has **no clean Play-only home**. If pursued, it ships as a **separate, signed direct-APK
  download** outside Play (an explicit exception to "Play only"), with checksums; otherwise it's
  deferred. Flagged as an open decision — see
  [platform strategy](03-platform-strategy.md#why-the-overlay-is-secondary-not-primary).

## Repository hygiene (and no machine-authored residue)

The repo must read like the work of a careful human team. This is both a quality bar and an
explicit requirement.

- **Commits:** Conventional Commits, imperative mood, scoped and meaningful. No tool-generated
  trailers, no attribution footers, no "generated by" lines, no co-author trailers for tooling.
- **History:** logical, reviewable commits — not one giant dump and not a hundred "fix typo"s.
- **Pull requests:** written like a person explaining intent and trade-offs; the PR template asks
  for *why*, testing done, and screenshots where relevant.
- **No AI tells in code or docs:** no boilerplate banners, no emoji-stuffed headings, no
  redundant "this function does X" comments on self-evident code, no uniform docstrings on
  trivial members, consistent and idiomatic naming. House style is enforced in
  [CONTRIBUTING.md](../CONTRIBUTING.md) and by lint.
- **Standard project files:** `LICENSE` (proprietary — all rights reserved), `CONTRIBUTING.md`,
  `SECURITY.md`, `CHANGELOG.md`, issue/PR templates, `CODEOWNERS`. The repository is private.
  Nothing references how the code was produced.
- **Generated artifacts** (SBOM, build outputs) live in releases/CI artifacts, not committed to
  source.

## Pre-release checklist

1. CI green including security guards and reproducibility.
2. Golden + false-positive corpus pass; fuzz clean.
3. Device-matrix smoke pass (Pixel + Samsung, one RTL locale).
4. Permissions reviewed; manifest still `INTERNET`-free.
5. Play Data Safety declaration reviewed and accurate.
6. CHANGELOG updated; version bumped; tag created.
7. Signed artifacts produced; checksums published.
